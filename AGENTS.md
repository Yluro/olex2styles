# olex2styles

3D drawing styles and GUI skins for [Olex2](https://www.olexsys.org), the crystallography program. Everything is generated by one script from Olex2's `light_g` style. There are two families:

- **modern**: neutral greys with vivid accents.
- **Flexoki**: built on the [Flexoki](https://stephango.com/flexoki) palette by Steph Ango.

## Hard rules

- **A refactor must leave the generated files byte-identical.** Check this before finishing:
  1. Copy `build_modern.py`, `light_g.glds` and `light_g.glsp` to a scratch folder (not `win/` or `macos/`).
  2. Run `python <scratch>/build_modern.py`; it writes `<scratch>/win/etc` and `<scratch>/macos/etc`.
  3. Run `diff -r win <scratch>/win` and `diff -r macos <scratch>/macos`. Both must print nothing.

  The outputs are CRLF; keep it that way.
- **Don't change any colour, palette value or skin name.** Every one was chosen with the user over many iterations. Comments may explain them; values stay.
- **Keep the first line of the skins:** `# Generated by build_modern.py ...`. `main()` uses it to delete stale skins it made earlier, and changing it would also break the identical-output check.
- **No new dependencies.** Standard library only (Python 3.8+; `math.dist` needs 3.8).
- **The user's style:** keep docstrings to one line where possible, and match the existing comment tone (short, says *why*).

## Layout

`win/etc` and `macos/etc` mirror Olex2's install folder, so installing means copying one of them over an Olex2 installation. They differ only in fonts (`PLATFORMS` in the script): `win` uses Trebuchet for the drawn images and Segoe UI for panel text and 3D labels; `macos` drops every font setting (`FONT_KEYS`) and keeps `light_g`'s 3D label fonts, because no Mac font setup has been tested.

```
build_modern.py   generator (run it from anywhere; paths are relative to the script)
light_g.glds/.glsp   INPUT: Olex2's own style, needed by the script
win/etc/styles/<style>.glds/.glsp   OUTPUT 3D styles: modern, modern_dark, flexoki_light, flexoki_dark
win/etc/skins/<skin>.phil   OUTPUT GUI skins (20)
macos/etc/...   the same files with Olex2's default fonts
docs/   preview images for the README
AGENTS.md   notes for coding agents (CLAUDE.md imports this file)
```

## Using the styles and skins in Olex2

Run these in Olex2's command line, e.g. `skin moderndark` then `load style modern_dark`.

- **Skins:** `skin <name>`.
- **3D styles:** `load style <name>`.
- **After regenerating:** run both commands again. Olex2 caches the last style (`last.osp`) and saves skin values into the user's `gui.phil`.

## Families and accents

Skins are named `<family><accent>`. The plain family name uses the default accent, orange; the user picked it because it is closest to the original Olex2 look.

| Family | Skins | Pairs with 3D style |
|---|---|---|
| modern (light) | `modern`, `modernmagenta`, `modernpurple`, `modernteal`, `modernblue` | `modern` |
| modern dark | `moderndark`, `moderndark{magenta,purple,teal,blue}` | `modern_dark` |
| Flexoki light | `flexokilight`, `flexokilight{magenta,purple,cyan,blue}` | `flexoki_light` |
| Flexoki dark | `flexokidark`, `flexokidark{magenta,purple,cyan,blue}` | `flexoki_dark` |

Each skin has two colours, like the original Olex2 look (blue buttons, orange highlights):

- **`ui`:** links, link buttons and action buttons. It is blue, or teal/cyan for the purple and blue accents, which would blend with blue.
- **`accent`:** the highlights (active tab, open section bar, pressed buttons, notices).

Red, yellow and green accents are left out because they read as the result grades.

The Flexoki skins use these Flexoki colours:

- **Greys:** panel base-100 or base-900; cards base-50 or base-850.
- **Accents:** the 600 shades in light, 400 in dark.
- **Result grades:** cyan, green, yellow, red, purple. Flexoki's own green, amber and red were too alike.

## Facts the code relies on (useful for accurate comments)

The full write-up, with a decoded example, is in "How the 3D styles are built" below. In short:

- **Olex2 data format:** `.glds`/`.glsp` are Olex2's XL data format; see `parse_xl`/`write_xl`.
- **Material strings:** `"Flags;AmbF;AmbB;DifF;DifB;SpcF;SpcB;ShnF;ShnB;EmsF;EmsB"`. Only fields whose flag bit is set are present.
  - Bits: 0x1/0x2 ambient, 0x4/0x8 diffuse, 0x10/0x20 specular, 0x40/0x80 shininess, 0x100/0x200 emission, 0x400 transparent, 0x800 identity draw.
  - Colours are decimal uint32 0xAABBGGRR.
- **Bitmap text in the 3D view is GL-lit:** only about 0.34× of an ambient colour reaches the screen. That is why labels, the console cursor and console messages get emission, or ambient plus diffuse.
- **Background:** the flat colour is the `.glsp` LightModel `ClearColor`; the gradient corners come from the `Background` entry.
- **Palette design:** atom colours are designed in OKLCH and checked with OKLab distances. `--report` prints those checks.
- **Dark styles:** atoms darker than OKLab L 0.58 are reflected lighter, with per-element overrides.
- **Skins:** `.phil` files override Olex2's `gui.params`. Skin names must not contain `_`.
- **Flexoki cards can't be paper `#FFFCF0`:** Olex2 draws the "i" info icons by darkening the card colour in HLS. Warm near-whites have HLS saturation 1, so the icons turn yellow.
- **The space-group text** on the title block is the panel base colour with its HLS lightness scaled by `sg_L`.

## Known Olex2 limits (good for a README "Known issues" section)

These come from Olex2 or Windows; a skin can't fix them.

- **Windows-drawn controls:** read-only combo boxes, checkbox squares and slider thumbs ignore the skin.
- **Status line:** the "X is loaded" / "Refinement finished" colour is read before skins load, so it always uses Olex2's built-in green.
- **Action buttons:** their white text is hard-coded in Olex2's panel HTML.
- **Graph colours:** some are hard-coded in Olex2's `Analysis.py`.
- **Image fonts:** each drawn element (title block, tabs, headers, image buttons) picks a font by a name from Olex2's font list (`util/pyUtil/PyToolLib/FontInstances.py`), through `timage.<element>.font_name`. `win` uses `Trebuchet` / `Trebuchet Bold`, which are in that list. On stock Olex2 a name outside the list breaks the panel images, and the file path and results-grid cells always use Signika.
- **Label font:** the `win` 3D label font is a Windows font string (Segoe UI); `macos` keeps `light_g`'s fonts.

## How the 3D styles are built

What `build_modern.py` writes into the `.glds`/`.glsp` files and why. The colour choices themselves are summarised in the README and explained next to each palette in the script.

An Olex2 3D style is a pair of files. `<name>.glds` says how each object is drawn; `<name>.glsp` sets up the scene around it. The `.glds` names its `.glsp` in its first line (`LinkFile="./etc/styles/modern.glsp"`). The generator reads Olex2's `light_g` pair, rewrites parts of it, and writes one pair per theme.

| File | Holds | What the generator changes |
|---|---|---|
| `.glds` | A table of materials, and one style entry per element and per overlay (labels, console, cursor, legend, background) | Atom colours and materials, overlay text colours, background gradient corners |
| `.glsp` | The light model (clear colour and 8 lights), the fonts, and the console message colours | Clear colour, a fill light, label fonts, console message colours |

### The file format

Both files use Olex2's own XML-like format. An item opens with `<Name`, lists its fields and child items, and closes with `>`. This is the copper entry of `modern.glds`, cut down:

```
<style LinkFile="./etc/styles/modern.glsp" Name="" Version="2"
 <Materials
  <Prop78 "85;4283066780;4283528106;4290366442;48">
  <Prop79 "85;4281089886;4280825939;4279045389;4">
  <Prop80 "1109;4283725745;2354675387;4283190348;16">
 >
 <Root Name="Root"
  <SubStyles
   <S_37 Name="Cu" PolyType="2" R="0.252458"
    <S0 PName="Sphere"
     <Material style.Materials.Prop78>
    >
    <S1 PName="Rims"
     <Material style.Materials.Prop79>
    >
    <S2 PName="Polyhedron"
     <Material style.Materials.Prop80>
    >
   >
```

- `Materials` is a shared table of material strings, `Prop0`, `Prop1` and so on.
- Each style entry (`S_0`, `S_1` …) names an element or object and lists its drawing primitives by `PName`. Each primitive points at a material as `style.Materials.PropN`. `R` is the atom's drawing radius.
- The generator writes every material inline first, then collects them into one table without duplicates, and renumbers the entries.
- Olex2 saves per-atom changes made during a session (an atom recoloured by hand) as extra `SubStyles` under an element; the generator drops these.

### Material strings

A material is a `;`-separated list: a flags number, then one value for each property the flags name, in the order ambient, diffuse, specular, shininess, emission. The flags are a sum of:

| 1 | 4 | 16 | 64 | 256 | 1024 | 2048 |
|---|---|---|---|---|---|---|
| ambient | diffuse | specular | shininess | emission | transparent | overlay (not rotated or zoomed) |

So `85` = 1 + 4 + 16 + 64 is a plain lit material, and `1109` adds transparency. Back faces have their own values (2, 8, 32, 128, 512); the generator sets only the front.

A colour is one decimal number that is `0xAABBGGRR` in hex: `4283066780` = `0xFF4A699C` = `#9C694A`, opaque. Shininess is a plain number; higher gives a smaller highlight.

The three copper materials above decode to:

| Primitive | Flags | Ambient | Diffuse | Specular | Shininess |
|---|---|---|---|---|---|
| Sphere | `85` | `#9C694A` (0.75 × colour) | `#AA7351` (0.82 × colour) | `#EACBB9` (colour mixed 55 % with white) | 48 |
| Rims | `85` | `#5E3F2C` (0.45 × colour) | `#533828` (0.40 × colour) | `#0D0D0D` | 4 |
| Polyhedron | `1109` | `#B17754` (0.85 × colour) | `#BB7E59`, alpha 140 (55 % opaque) | `#4C4C4C` | 16 |

Copper's colour is `#D08C63`; each material is that colour scaled or mixed.

### Lighting, and why text needs emission

The scene's main light (`Light0` in the `.glsp`) has an ambient of `0x575757` (0.34), a diffuse of `0xEAEAEA` (0.92) and a white specular. A surface therefore shows about 0.34 × its ambient colour everywhere, plus up to 0.92 × its diffuse colour where the light hits it, plus the specular highlight. The generator also switches on `Light1`, a weak grey fill light from the lower right, so the shadow side of the atoms isn't flat.

Olex2 lights its bitmap text too. A text material with only an ambient colour, like `light_g`'s cursor and console messages, shows at about a third of its brightness: dim messages and a near-invisible cursor on a dark background. The generator gives text its exact colour in three ways:

| Text | Flags | How |
|---|---|---|
| Atom labels (`labels` command) | `3333` | Emission, which is added unlit, so the colour shows as is |
| Console messages (errors, warnings, help) | `2305` | Ambient plus emission at 0.66 × the colour |
| Console text and cursor | `2053` | Ambient plus diffuse |

The other overlays (legend, grid labels, help window) are recoloured in place.

### How each atom's colour and material are chosen

For every element entry in `light_g.glds`, the generator does this:

1. **Kept elements.** C, H, N, O, F, Cl and S keep their `light_g` sphere materials, which chemists already recognise. Only C is made slightly greyer (0.82 ×) so H stands out, and F is turned 10° greener so it stays apart from S.
2. **Other elements.** Their colour comes from the script's palettes: the d-block, lanthanides and main-group metals, plus Br. Elements not in a palette (alkali and alkaline-earth metals, actinides, most non-metals) keep their `light_g` colour but get the new materials.
3. **Sphere material.** The finish (`--finish`) sets how the colour is scaled:

   | Finish | Ambient | Diffuse | Specular grey | Shininess |
   |---|---|---|---|---|
   | satin (default) | 0.85 × | 0.90 × | 0.30 | 16 |
   | matte | 0.88 × | 0.92 × | 0.04 | 4 |
   | glossy | 0.82 × | 0.85 × | 0.75 | 80 |

   The specular is a grey, so the highlight never tints the atom. Polished metals (Cu, Ag, Au, Pt, Pd, Rh, Ir, Os, Ru, Hg, Re, Ta, W) use a metallic recipe instead: a highlight tinted with the metal's own colour, and shininess 48.
4. **Iridium** gets a fake thin-film sheen. Because the lighting adds the three terms, a violet ambient, a teal diffuse and a gold specular show as a violet edge, a teal body and a gold glint.
5. **Rims**, the rings drawn around a sphere, are a darker shade of the atom's own colour (`--rims dark`). `--rims neutral` uses a grey instead, and `--rims keep` keeps `light_g`'s.
6. **Polyhedra.** Metals also get a translucent coordination-polyhedron material, 55 % opaque.

**The palettes are written in OKLCH**, a perceptual colour space: L is lightness (0 to 1), C is chroma (0 is grey, about 0.2 is vivid) and h is the hue angle in degrees. Equal steps look about equally large, so lightness and saturation can be balanced across elements. A colour that falls outside what a screen can show keeps its lightness and hue and loses chroma.

Each palette colour has a reason, noted next to it in the script: a salt, mineral, name or property of the element. Examples are Dy₂O₃ sand for dysprosium, the red and green emission of Eu³⁺ and Tb³⁺, and cadmium-pigment orange for Cd. The metals were then tuned to stay apart from each other, from the lanthanides and from the ligand atoms around them (N, O, P, Cl, C). `--report` prints these colour distances, measured in OKLab.

**Dark themes** lighten dark atoms so they don't vanish on the background. A colour with lightness L below 0.58 moves to 0.58 + 0.9 × (0.58 − L). It is mirrored above 0.58, so dark atoms keep their order, just lighter: tantalum and tungsten become a pale gunmetal. A few elements are exceptions where the mirrored colour would clash with a neighbour: O isn't lightened, and Hg, Hf, Br and Rh get their own dark-theme colour.

### The scene file (`.glsp`)

| Section | What it does | Generated value |
|---|---|---|
| `LightModel` `ClearColor` | The flat background colour | The theme's background, e.g. `#E4E5E8` for modern |
| `Light0` to `Light7` | The scene's lights | `Light0` as in `light_g`; `Light1` turned on as a grey fill light |
| `Fonts` | Fonts of the 3D view's text | `win`: labels in Segoe UI Semibold; `macos`: `light_g`'s fonts. Console and help keep Olex2's bitmap font (`#olex2.fnt:frb_12`) |
| `Materials` | Console message colours (`Error`, `Warning`, `Info`, `Help_cmd`, `Help_txt`, `Exec`) | Theme colours with flags `2305` |

Two font slots matter for labels:

- `Labels` is the font of the `labels` command (all atom labels at once), the unit-cell labels and the axes.
- `AtomLabels` is the font of single atom labels and the atom legend.

Fonts other than the bitmap one are stored as Windows font descriptions (`1;16;-21;0;0;0;600;…;Segoe UI Semibold`: size in points, height in pixels, weight, face). Olex2 on other systems falls back to its default font.

### The background

With the gradient off, Olex2 fills the background with `ClearColor`. With it on (the `grad` command, or F4), it uses the four corner colours of the `Background` entry in the `.glds`: `A` and `B` at the bottom, `C` and `D` at the top. Whether the gradient is on is an Olex2 setting, not part of the style.

The matching skin carries the same background colour, gradient corners and label font, because Olex2 re-applies them from the skin whenever the skin changes. That is why each skin family pairs with one 3D style.

### How Olex2 loads a style

- `load style <name>` reads the `.glds`, then the `.glsp` it links to.
- Olex2 restores the last style you used from `last.osp` in your user data folder. It also saves a copy with each structure, in the structure's `olex2` folder. A regenerated style therefore shows only after you run `load style` again.
- Load the style before opening a structure, or the atom legend keeps the old colours.
- An element missing from a style falls back to Olex2's built-in colour.
